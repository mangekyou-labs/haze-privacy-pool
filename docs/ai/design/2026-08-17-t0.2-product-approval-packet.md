# T0.2 product approval packet

**Feature:** `haze-avalanche-compliant-pool`
**Branch / worktree:** `feature-haze-avalanche-compliant-pool`
**Date:** 2026-08-17
**Decision:** approve, reject, or approve with named conditions the freeze of Haze Avalanche
protocol v1 encodings and the v1 threat model.

This packet is the product half of the T0.2 exit gate. Independent cryptography and EVM review
`91cfa5ee` already accepted the encodings. The three review follow-ups are implemented. Product
approved this packet in-thread on 2026-08-17 with no conditions. T0.2 is closed. T1.1 is unblocked
and has not started.

Normative encoding rules live in
[`2026-08-10-haze-avalanche-protocol-v1.md`](./2026-08-10-haze-avalanche-protocol-v1.md).
This packet does not replace that spec. It states the product decisions that become expensive to
change after T1.1 starts.

## What yes unlocks

Approving this packet closes T0.2 and unblocks **T1.1 only**: review and adapt reusable privacy
primitives (Poseidon2, Merkle, note, nullifier, encryption concepts) to these frozen encodings.

Approving this packet does **not** authorize:

- production spend circuits, proving keys, or verifier bytecode;
- a HazePool contract, router, or registry;
- live DEX, RPC, KMS, identity, or object-store adapters;
- Fuji pilot funds, C-Chain mainnet, or a trusted-setup ceremony;
- changing FR-01 through FR-06 after the fact without a new versioned protocol.

A later “go to Fuji / mainnet” decision remains a separate operational and security gate.

## What is being frozen

| Area | Frozen v1 choice |
| --- | --- |
| Product | One shared, USDC-only compliant privacy pool on Avalanche C-Chain (Fuji first). |
| Privacy start | Privacy starts when USDC is committed to the pool. Source-token swaps are public. |
| Actions | `1` deposit, `2` transfer, `3` withdraw, `4` swap-and-shield, `5` emergency-exit. |
| Assets | Shielded value is USDC base units (`u64`). Circle USDC Fuji `0x5425890298aed601595a70AB815c96711a31Bc65`; C-Chain `0xB97EF9Ef8734C71904D8002F8b6Bc66Dd9c48a6E`. |
| Networks | Fuji `43113` and C-Chain `43114` are distinct pool domains. Notes, proofs, and addresses do not transfer across them. |
| Application binding | Every normal action is bound to one application. Cross-application private spends and outputs are invalid in v1. |
| Authorization | Normal actions require a registered gatekeeper EIP-712 authorization (user, application, pool, action, intent hash, both policy versions, audit commitment and ciphertext hash, nonce, expiry). |
| Policy | Two-tier: application membership root plus Haze global blocklist non-membership. No post-activation grace period. Stale, future, or unknown roots fail closed. |
| Emergency exit | User registers an opaque request, waits seven days, then withdraws one complete note to a public address without a gatekeeper or application-membership proof. Haze global blocklist still applies. |
| Addresses | App-scoped `haze1:` addresses carry spending public key + X25519 encryption key + application / chain / pool-version binding. |
| Encryption | Separate recipient and audit HPKE channels (RFC 9180 Base, X25519 / HKDF-SHA256 / ChaCha20-Poly1305). Same suite, different keys, labels, and payloads. |
| Audit truth | Circuit recomputes `audit_data_commitment` from real private fields and a hidden salt. Gatekeeper assertions are not circuit-proven identity. |
| Hash split | Poseidon2 in-circuit; Keccak-256 for EIP-712, envelopes, address checksums, and manifests. |
| Identifiers | Opaque `bytes32` values are two uint128 limbs. They are never reduced modulo the field except for the 13 frozen Poseidon domain constants. |

## Decisions product must accept

Check each item. A blank item is a reject or a condition, not an implicit yes.

### D1. Public metadata is not private

On-chain and in product copy, these remain public: wallet submitter, application affiliation,
source-token swap, deposit and withdrawal amounts and recipients, gas, ciphertext sizes, timing,
and public version migration. Marketing and UI must not call these values private.

- [x] Accept

### D2. Anonymity set is application-local in practice

One shared USDC tree exists, but public gatekeeper authorization reveals the application. The MVP
also forbids cross-application private value movement. Users of application A do not mix privately
with users of application B.

- [x] Accept

### D3. Gatekeepers can censor; they cannot steal

A registered application gatekeeper may refuse to authorize a normal action or may attach false
application assertions. It cannot spend a user note, rewrite circuit-proven facts, or skip the
seven-day emergency exit. Product must describe this honestly to integrators and users.

- [x] Accept

### D4. Two-tier compliance is the product, not an add-on

Every enabled note in a normal proof must show application membership **and** Haze global
non-membership (note key; public payer/recipient also screened as EVM addresses where applicable).
Haze operators control the global list through timelocked roots. Applications control their own
eligibility list. Haze is not a KYC vendor and does not hold a shared customer identity database.

- [x] Accept

### D5. Audit records are application-scoped and key-sensitive

The application controls the versioned audit HPKE key. Authorized institutional auditors can
decrypt that application’s retained records. They cannot read recipient-note envelopes or other
applications’ records unless a later, separately granted super-auditor path is designed.

- Audit-key outage denies disclosure; it does not lock or spend notes.
- Audit-key compromise exposes that application’s retained audit records.
- Emergency-exit audit envelopes are built client-side because no gatekeeper participates.

- [x] Accept

### D6. Emergency exit is the liveness guarantee

If an application is suspended, offline, or refusing authorization, a note owner can still exit
after seven days to a public EVM address, subject to the current Haze global blocklist. That
withdrawal is public. There is no private change output on emergency exit.

- [x] Accept

### D7. Swap-and-shield stays public until the shield

The router accepts only configured source tokens and routes, swaps to USDC in public, and
atomically shields the result. The pool does not retain user funds on a failed swap. There is no
in-pool AMM, multi-asset shielded pool, or private source-token swap in v1.

- [x] Accept

### D8. Deposit shape

A deposit creates new notes from public USDC. It does not spend existing notes, so
`noteTreeRoot` and both input nullifiers must be zero. Swap-only fields must be zero on every
non-swap action.

- [x] Accept

### D9. Fuji first; C-Chain is a later activation

Development and vector work bind Fuji (`43113`) and C-Chain (`43114`) as separate domains. Shipping
encodings does not ship mainnet. C-Chain activation still requires the Fuji pilot, independent
audit, production trusted setup, and operational-readiness review named in the requirements.

- [x] Accept

### D10. Encoding freeze is a versioned protocol

Unknown versions, unknown algorithm suites, non-canonical encodings, omitted required fields, and
unknown fields are rejected. A rejected v1 value is not reinterpreted as a legacy format. Breaking
any item in this packet after T1.1 starts requires a new protocol version, not a silent patch.

- [x] Accept

## Requirements covered by this freeze

T0.2 freezes the encodings and trust boundaries that FR-01 through FR-06 and FR-12 / FR-13 depend
on. It does not implement those features.

| Requirement | Encoding / policy freeze |
| --- | --- |
| FR-01 Pool | Shared USDC pool actions, 2-in/2-out notes, public amount, historical roots. |
| FR-02 Application binding | Application ID on notes; membership + global non-membership; no cross-app private value. |
| FR-03 Authorization | EIP-712 intent + application authorization types, nonce, expiry. |
| FR-04 Policy | Membership root, sorted-blocklist non-membership, no grace period. |
| FR-05 Swap-and-shield | Public swap-only fields; zero unless action is swap-and-shield. |
| FR-06 Truthful audit | Circuit-bound audit commitment; separate HPKE audit envelope; CBOR record. |
| FR-12 Emergency exit | Separate 20-field public-input order; request-id encoding; no gatekeeper. |
| FR-13 Recipient delivery | `haze1:` / `HZAV` address; recipient HPKE envelope and hash. |

FR-07 through FR-11 and FR-14 (indexing, auditor access, disclosure, portals, governance, version
migration) remain later tasks. They must consume these encodings; they do not reopen them.

## Trust model (ADR-0003)

| Actor | Trusted for | Not trusted for |
| --- | --- | --- |
| User wallet | Spending secret, X25519 private key, EIP-712 consent | Hiding a blocked note or mixing applications |
| Application gatekeeper | Membership-root authenticity for its application | Haze global blocklist or other applications |
| Haze policy operators | Timelocked global blocklist root | Application KYC membership |
| Institutional auditor | Decrypting audit envelopes they are authorized to open | Learning recipient HPKE payloads |
| Pool contract | Custody, nullifiers, root history, proof verification | Reconstructing private note fields |
| Relayer / RPC / DEX | Availability | Authorization, value conservation, policy freshness |

Explicit non-goals of this freeze: no production circuit, verifier, or HazePool bytecode; no
vendor types in public APIs; sorted blocklist (not an SMT); depth-32 Merkle trees with
domain-separated empty roots.

## Residual risks accepted by a yes

These are known and are not treated as T0.2 blockers:

1. Poseidon2 permutation is Rust/`zkhash` reference only until T1.1 Circom gadgets exist. A
   Circom mismatch later is a release blocker, not a silent “close enough.”
2. Public application authorization shrinks the effective anonymity set to the application.
3. Gatekeeper censorship and false application assertions are in-scope residual risks; emergency
   exit is the user-liveness backstop.
4. Application audit-key compromise discloses that application’s retained audit records.
5. Relayers, RPCs, and DEX quotes are availability-only; they must not be described as policy or
   custody authorities.
6. Contract-wallet / account-abstraction key derivation is unsupported until a separately reviewed
   adapter exists.
7. No production circuit, verifier, or pool contract exists yet. Encoding approval is not a
   security audit of those future artifacts.
